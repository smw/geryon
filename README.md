# geryon

A webtiles server for [Dungeon Crawl Stone Soup](https://github.com/crawl/crawl),
as a single static binary. It replaces the Python/Tornado server in
`crawl-ref/source/webserver` and serves crawl's own browser client unchanged;
crawl itself is not modified.

Named after the gatekeeper of the Vestibule of Hell.

## Status

Working for a personal or small shared server: accounts, lobby, playing,
spectating, chat, rc editing, in-progress locks and ttyrecs.

Not implemented: password reset by email, the admin panel's actions, ban
lists, milestone files, the dgamelaunch status file, adopting games started
outside the server, TLS (put a reverse proxy in front), and reloading the
configuration on a signal. `config.py` is not read; see Configuration.

## Running

You need a crawl checkout built with webtiles support:

```sh
cd crawl/crawl-ref/source
make WEBTILES=y
```

Then run geryon from that same directory, as you would the Python server:

```sh
cd crawl/crawl-ref/source
/path/to/geryon            # listens on port 8080 by default
```

Stop the Python server first if it uses the same port. Existing accounts
(`webserver/passwd.db3`), rc files, saves and `games.d` definitions are used
as they are.

Options: `-server-path DIR` (where `config.yml` and `games.d/` are; default
`./webserver`), `-port N`, `-address ADDR`, `-version`.

## Configuration

Settings are read from `config.yml` in the server path, with the same names
and meanings as the Python server's options. Games come from `games.d/*.yaml`
there, or from the stock list built into the binary if that directory does
not exist. An option geryon does not act on is reported at startup.

Differences worth knowing:

- New password hashes are always SHA-512 (or SHA-256 with
  `crypt_algorithm: "5"`). Old DES hashes still verify.
- `static_path` and `template_path` are optional. When unset, the copies built
  into the binary are served; set them to serve from disk, for instance while
  editing the client's scripts.
- A game whose `client_path` does not exist on disk gets the game client built
  into the binary, which matches the crawl version shown by `geryon -version`.

## Building

The browser client belongs to crawl and is partly generated by its build, so
it is not in this repository. `make` copies it from a crawl checkout:

```sh
make client CRAWL_SOURCE=/path/to/crawl/crawl-ref/source   # once, and after crawl changes
make build
```

`CRAWL_SOURCE` defaults to `../crawl/crawl-ref/source`.

## Testing

```sh
make check        # gofmt and go vet
make test         # needs the crawl checkout; about a minute
make test-short   # skips the test that waits out a twenty-second timeout
```

Most tests start the server in-process and play real crawl games through it
over WebSocket, as a player and as spectators. Without `GERYON_CRAWL_SOURCE`
(which `make test` sets) those tests are skipped.

## How it is put together

- A **session** per browser connection handles that browser's requests.
- A **game** per crawl process relays between crawl and the browsers seated
  at it, and owns everything about that game: process, socket, roster, chat.
- The **hub** holds the little that is shared: the lobby's list of games, who
  is connected, login tokens.

Each session and game runs on its own goroutine. Waiting only goes one way
(session, then game, then hub), and output to browsers goes through a
per-connection outbox that never blocks the sender, so a slow browser or a
stuck game delays only itself.

## Continuous integration and releases

Every push builds crawl at the commit named in `CRAWL_VERSION` (cached), runs
the tests against it and builds Linux archives for amd64 and arm64. Pushing a
tag starting with `v` publishes those archives as a GitHub release:

```sh
git tag v0.1.0 && git push origin v0.1.0
```

To move to a newer crawl, change the commit in `CRAWL_VERSION`.
